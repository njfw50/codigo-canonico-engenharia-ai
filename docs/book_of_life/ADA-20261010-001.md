## 2. Decisions and alternatives

| Decision | Rationale and boundary |
| --- | --- |
| Implement three explicit actions with a host-owned policy boundary | Makes concrete failure paths observable without inventing a universal risk classifier. |
| Permit narrowly delegated autonomy and narrowly bound confirmations | Preserves useful automation while constraining scope, freshness and actual consequences. |
| Separate JSON, audit, gateway and evaluation responsibilities | Keeps the execution path reconstructible with no external dependency or ornamental framework. |
| Serialize and reserve attempted ID/count/spend before asynchronous dispatch | Prevents in-process concurrent overspend and automatic retries after uncertain outcomes. Durable multi-process state remains a host requirement. |
| Require pre-action audit and preserve observed/uncertain post-action outcomes | An unavailable record blocks a new attempt; a later failure cannot hide an action already dispatched. |
| Use linked audit records with a separately trusted checkpoint | Hashing demonstrates integrity under a stated trust anchor; local hashing is not immutable storage or authentication. |
| Publish independent fixture labels and a deliberately unprotected baseline | Demonstrates the mechanism on constructed inputs; does not claim superiority over other SI systems or general productivity gains. |
| Preserve all original source/record bytes and keep archived citation names | Changes terminology in current presentation without falsifying published sources or sealed history. |
| Keep the existing installation hook outside scope | No installation is needed for examples/checks; unrelated bootstrap behavior is neither executed nor altered. |

## 3. Interfaces and comprehension

The [specification](../superpowers/specs/2026-10-10-operational-delegation-design.md) and [implementation plan](../superpowers/plans/2026-10-10-operational-delegation.md) identify exact modules and boundaries. The [walkthrough](../../examples/delegation/README.md) explains policy authority, preview, human-channel confirmation, dispatch, reservation and uncertainty. Comments explain why the controls exist; the [reconstructive review](../operational/GOVERNANCE.md) asks the human to reconstruct the path.

`confirm` is a host assertion after actual human-channel approval. It is not proof of identity and must not be available as an SI tool. The raw adapter, policy, context and persistence must also be isolated by the host. In-process state and memory logs do not imply restart-safe or distributed guarantees.
